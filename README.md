# RK1828 大模型 Demo、性能与稳定性测试

本项目围绕 RK1828 端侧大模型，提供交互演示、性能测试和稳定性测试，重点展示实际运行效果，并验证不同负载下的响应速度与持续运行表现。

| 核心方向 | 主要内容 | 展示结果 |
| --- | --- | --- |
| Demo 演示 | 流式对话、多轮问答、长文本摘要、结构化输出 | 实际回答、运行状态和实时性能 |
| 性能测试 | 首 token 延迟、Prefill/Decode 速度、吞吐、长输入与并发 | 单请求基线、负载对比和性能边界 |
| 稳定性测试 | 长时间运行、循环请求、异常恢复和资源监控 | 成功率、失败记录、性能趋势及资源曲线 |

> 项目状态：方案设计阶段。以下为功能规划与 SDK 接入说明，目前尚未提供完整可运行的 Demo 或板端实测成绩。

## 技术路线

采用 RK182x SDK 的 RKNN3 / RKLLM3 工具链，参考 Release V1.0.4 接口。部署时以所使用版本的文档为准。下文 `<SDK>` 表示 SDK 根目录。

RK1828 是协处理器，服务、模型文件及调度程序运行在 Host 上，Host 经 PCIe / USB / Ethernet 与 RK1828 通信。ADB 通常用于连接 Linux/Android Host，不能把 ADB 设备列表直接当作 RK1828 枚举结果。芯片识别应在实际 Host 上通过 `rknn-smi` 完成。

### SDK 组件

| 用途 | SDK 路径（相对 `<SDK>`） | 本项目处理方式 |
| --- | --- | --- |
| 流式对话服务 | `rknn/rknn3-runtime/rkllm3-server/` | 复用 `rkllm3-server`，接入 `/health`、`/v1/models`、`/v1/chat/completions` |
| 现成对话网页 | `examples/web/` | 参考交互及模型管理，补充预置演示场景和准确的客户端计时 |
| 现成性能网页 | `examples/ai_hub/` | 参考 `backend/llm.py` 的日志流和参数界面，其调用 `rknn3_llm_demo` |
| 可审查的原生性能基线 | `rknn/rknn3-model-zoo/tools/rknn3_llm_test/` | 使用 `rknn3_session_test_eval_perf`，采集 TTFT、Prefill、TPOT、Decode TPS |
| C/C++ 会话与工具调用 | `rknn/rknn3-runtime/examples/rknn3_session_test_demo/` | 需要时参考 Session API 与 Function Calling 示例 |
| 设备遥测 | `docs/Tools/`、`examples/monitor/` | 使用单一采集器调用 `rknn-smi`，提供统一状态缓存 |

第一版先复用现成服务与测试二进制，在外围补充任务管理、准确统计和结果保存。网页参考 SDK 的 Flask 示例，按需求扩展演示、性能与稳定性测试功能。

### 模型与部署方式

优先用与目标板 SDK 匹配的预转换小模型完成冒烟测试，例如 Quick Start 中的 Qwen2.5-0.5B，再依据实际内存选择 Qwen2.5-3B 或 Qwen3 系列进行演示与对比。SDK 列出模型适配不等于任意规模都能在当前板卡上运行。

典型模型包为 `.rknn`、`.weight`、`.tokenizer.gguf`、`.embed.bin`；权重是否分离以实际模型为准。此处 `.gguf` 是 tokenizer 文件，不是直接加载完整 GGUF 大模型。自行转换时使用 RKNN3 Toolkit 和对应 Model Zoo 导出脚本。

部署前需准备与 Host 操作系统、CPU 架构和 SDK 版本匹配的运行时与服务程序，并完成驱动及固件配置。

以下是 Linux Host 上的 SDK 服务启动示例，不是本项目的一键启动命令。假设所需工具已安装，并已准备对应模型包；路径和文件名需按实际情况修改。

```bash
# 识别芯片、连接方式及版本
rknn-smi info
rknn-smi info -l
rknn-smi -v
systemctl status rknn3 --no-pager

# 已准备好匹配版本的 Qwen2.5-3B 示例模型包时启动
cd /userdata/models/Qwen2.5-3B
rkllm3-server -m Qwen2.5-3B-Instruct.rknn \
  --weight Qwen2.5-3B-Instruct.weight \
  --vocab Qwen2.5-3B-Instruct.tokenizer.gguf \
  --embed Qwen2.5-3B-Instruct.embed.bin \
  --alias demo-llm --host 127.0.0.1 --port 8080 -c 0

# 在另一终端验证；网页后端在本机访问，跨机访问另行配置转发
curl http://127.0.0.1:8080/health
curl http://127.0.0.1:8080/v1/models
curl -N http://127.0.0.1:8080/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{"model":"demo-llm","messages":[{"role":"user","content":"请用一句话介绍你能做什么。"}],"stream":true,"n_predict":128,"cache_prompt":false,"id_slot":0}'
```

### 统计与资源约束

1. **分开测试原生性能与 HTTP 体验。** 原生工具测 Session 调用，HTTP 压测包含客户端、网络和排队，两组数据不能混称一个 TTFT。
2. **官方随机输入性能测试不评回答质量。** 参考版本的工具固定随机种子、执行 3 轮、每轮清理 KV cache，并在最后输出最后一轮摘要；摘要不是三轮平均。工具 README 要求排除第一轮初始化影响，因此保留逐轮结果，另行计算稳态统计。
3. **统一客户端统计。** 从发起请求前用单调时钟计时，跳过空事件；服务端 `timings.prompt_ms` 与客户端首内容延迟分别保存。流式 chunk 数不等于 token 数，缺少真实 token 数时不报 tokens/s。
4. **上下文由模型转换配置限制。** `max_ctx_len`、位置编码上限和 HTTP 模型元数据不是同一概念；不能仅按 `/v1/models` 的 `n_ctx_train` 设置压测长度。先查询实际模型配置，再安排输入/输出预算。
5. **核数不是任意旋钮。** Quick Start 要求通过 `RKNN3_QUERY_CORE_NUMBER` 查询模型所需核心数，`core_mask` 的选中数量需匹配。AI Hub 的核数选项不能无条件用于同一个模型的核数扫描。
6. **并发需要明确会话归属。** Server 提供 `--n-session`，默认 1；请求 `id_slot` 默认为 0 且必须小于 session 数。先单会话验证，再设置 2/4 个 session、为各客户端分配独占 slot，并测试隔离、调度和内存变化。此后才测试超过 session 数的请求排队压力。`--params-file` 可配置多模型，但本期暂缓多模型常驻。
7. **单一遥测采集器。** Monitor README 明确 SMI API 的单线程限制及多个 Demo 采集冲突；界面统一读取采集缓存。功率取决于硬件采样支持，缺失记为 NA，不把示例 Monitor 的 0 当作真实零功耗。
8. **固定性能环境。** 保存 work mode、prefill mode、温度与频率；初期沿用当前模式测试，不自动切换频率或温控策略。聊天常驻服务可能占用设备资源，原生独占基线应在计划内释放聊天模型后运行，并记录服务状态。

### 实施顺序

1. 查明实际 Host、RK1828 型号/内存/接口及软件版本，找到匹配的完整模型包。
2. 跑通 `rknn3_session_test` 和原生性能工具，建立可重复的单模型基线。
3. 启动 `rkllm3-server`，用 curl 验证流式协议、结束原因、实际 `usage/timings` 字段。
4. 接入网页的四类文本场景，增加客户端计时、原生指标展示、测试记录与导出。
5. 完成长输入、独立 session 并发及持续运行测试；YOLO、多模型常驻和 VLM 作为后续扩展。

## 1. 项目范围

第一版围绕一个已在设备上验证可运行的文本大模型，完成交互演示、性能压测和稳定性验证闭环。覆盖问答、摘要和结构化抽取等混合任务负载，YOLO 与多模型组合不纳入第一版范围。

评测结论必须绑定具体的模型、量化方式、上下文配置、SDK、宿主机和 RK1828 硬件配置。同一个模型的表现不能直接代表芯片上所有模型的表现。

| 方向 | 需要回答的问题 | 展示或交付 |
| --- | --- | --- |
| Demo 演示 | 能否顺畅展示中文对话、摘要、抽取等真实任务？ | 实际输入输出、交互状态和实时指标 |
| 交互性能 | 首次响应等待多久？持续生成是否流畅？ | 首字延迟、生成速度、总耗时 |
| 负载边界 | 长输入、长输出、多请求会如何影响体验？ | 各负载档位的延迟、吞吐和错误率 |
| 稳定性 | 长时间运行是否出现泄漏、降速或失败？ | 时间序列、错误日志和可用资源遥测 |
| 可复现性 | 同一配置能否复测并比较？ | 配置快照、逐请求记录和汇总报告 |

## 2. 演示怎么做

### 2.1 首页：设备与模型概览

展示连接状态、宿主机与 RK1828 配置、运行时版本、当前模型、量化方式和模型上下文上限。无法读取的字段显示“未知 / 未采集”。

连接后先运行一次健康检查和短问答。只有推理成功后才进入“可演示”状态。现场显示推理服务地址与执行后端，并保留板端运行日志，便于确认推理实际运行在目标设备上。

### 2.2 大模型交互演示

提供流式聊天窗口、预置场景按钮和每轮性能信息。第一版建议提供以下四个场景：

| 场景 | 演示内容 | 观察重点 |
| --- | --- | --- |
| 中文多轮问答 | 先给出设备需求，再追问并修改约束 | 上下文理解、约束遵守、响应速度 |
| 长文本摘要 | 对一份固定的设备说明或会议记录做摘要 | 长输入处理、关键事实保留、遗漏与编造 |
| 结构化信息抽取 | 从报修描述中提取设备、故障、时间等字段，输出 JSON | JSON 合法性、字段准确率、指令遵循 |
| 简单推理与任务分解 | 根据给定规则安排任务，输出结论与简短依据 | 结果正确性、规则遵守、步骤可执行性 |

每个预置场景包含可重复使用的输入和基本输出检查，保留失败案例。演示回答直接来自设备，并展示本轮首内容延迟、生成速度和总耗时。第一版不建设独立的模型能力排行榜或综合评分体系。

推荐现场流程：查看设备与模型 → 中文多轮对话 → 长文本摘要 → JSON 抽取 → 运行一组短压测 → 查看结果。现场流程控制在约 5～10 分钟；长稳测试提前执行并展示历史报告。

### 2.3 压测控制台

支持选择模型、测试集、输入长度、输出上限、并发档位、请求数或运行时长。运行时展示进度、完成数、失败数和实时指标，并可停止任务。

停止操作首先停止发起新请求；是否能够取消已进入板端的推理取决于运行时接口。停止后仍保存已完成及已失败请求的记录。

### 2.4 结果页

展示本轮配置、延迟分布、吞吐、错误分类以及资源变化。可以在相同测试集下比较不同模型或配置，并导出 JSON、CSV 和 HTML 报告。

模拟数据仅用于界面联调，必须明确显示“模拟模式”，不得进入实测排行榜或报告。

## 3. 大模型压测方案

### 3.1 核心指标与统计口径

| 指标 | 口径 |
| --- | --- |
| 首内容延迟（TTFT） | 客户端发起请求至收到首个非空生成内容的时间；忽略角色字段、空事件及心跳。流式分块不一定等于单个 token，报告中注明观测方式 |
| 端到端耗时 | 请求发起至完整响应结束，包含排队、网络传输与生成 |
| 单请求生成速度 | 优先使用运行时报告的 decode tokens/s；只能客户端测量时，使用明确标注的估算口径，不与原生指标混用 |
| 总吞吐 | 测量窗口内成功完成请求的输出 token 总数 / 窗口耗时，同时报告成功 requests/s |
| 延迟分布 | TTFT 和端到端耗时的 P50、P95、P99，附样本量；小样本尾部结果仅作参考 |
| 成功率 | 成功完成请求数 / 实际发起请求数；超时、接口错误、流中断、取消分开统计 |
| 输出有效性 | 检查空响应、异常终止和结构化场景的 JSON 合法性，避免将无效输出当作正常完成 |
| 资源与稳定性 | 能采集到的宿主机/加速器内存、温度、功耗、利用率和频率，注明采样来源与间隔 |

Token 数优先来自推理服务的 usage 或匹配模型的 tokenizer。若二者都不可用，只报告字符数、字符速度和耗时，token 指标显示“不可用”，不得用字符数冒充 token 数。推理内容与最终回答是否分别计数，应按模型和运行时能力说明。

冷启动、模型加载、预热请求和正式测试分开记录。失败请求不进入成功延迟分布，但必须保留失败耗时、原因和占比，避免只统计成功样本掩盖过载问题。

### 3.2 测试矩阵

以下为候选档位，需根据板卡内存、模型上下文上限和运行时能力调整。输入 token 数与输出预算之和不得超过实际可用上下文窗口。

| 测试 | 建议起点 | 目的 |
| --- | --- | --- |
| 连通与冒烟 | 单请求、短输入、短输出 | 确认模型可用、流式协议可解析 |
| 单请求基线 | 并发 1，预热后正式执行 30 个请求 | 建立交互延迟与生成速度基线 |
| 输入长度扫描 | 约 512 / 2K / 4K / 8K tokens，逐档验证 | 测试长输入对首内容延迟和内存的影响 |
| 输出长度扫描 | 最大生成 128 / 512 / 1024 tokens | 观察生成阶段表现；记录实际输出长度和结束原因 |
| 并发扫描 | 1 / 2 / 4 / 8，逐档递增 | 测量排队、总吞吐、失败率和饱和点 |
| 混合任务 | 短问答、摘要、JSON 抽取交替执行 | 模拟实际业务请求组合 |
| 持续运行 | 先 30 分钟，再按结果扩展至 2 / 8 小时 | 观察降速、资源增长、失败与恢复 |
| 异常与恢复 | 请求超时、客户端取消、服务不可用 | 验证错误展示、结果落盘和恢复后的可用性 |

并发请求不等于硬件并行推理。需识别服务端串行排队、多实例或批处理行为，报告实际调度方式。第一版使用固定并发的闭环压测；如需衡量外部请求到达压力，再增加按固定到达率发起请求的测试，并记录排队时间。

每轮固定模型、采样参数、提示词模板和缓存策略。记录随机种子（如支持）、重复前缀缓存情况及实际 token 数。输入长度测试采用可复现文本，并检查截断；长上下文测试同时放置可验证事实，检查模型是否仍能正确提取。

达到配置的错误率、超时或资源阈值时停止升档并保存结果。温度等阈值由板卡规格确定，未确认前不设置虚构的芯片安全阈值。长稳测试需设置明确结束时间。

### 3.3 稳定性专项

稳定性测试使用固定场景集循环发起请求，保持模型、上下文、并发和采样参数一致。先执行 30 分钟验证，再扩展到 2 小时和 8 小时；测试时长可配置。

| 检查项 | 记录内容 |
| --- | --- |
| 持续可用性 | 总请求数、成功率、超时数、连续失败次数、最长连续运行时间 |
| 性能变化 | 按固定时间窗口统计首内容延迟、Decode 速度和吞吐，对比预热后的基线 |
| 资源变化 | Host 与加速器内存、温度、频率、利用率及可获取的功耗 |
| 异常行为 | 进程退出、流中断、空响应、设备不可用及关联日志 |
| 恢复能力 | 超时或断连后新请求能否成功，服务恢复至首次有效回答的耗时 |

默认记录异常并按配置停止，不用静默重试掩盖失败。如果开启重试，原始失败、重试次数和恢复耗时分别统计。故障注入与自然长稳分开执行并标注；故障恢复测试中的中断不混入自然运行的故障率。

长稳报告包含运行时长、有效样本数、失败时间线、资源曲线、性能变化及退出原因。内存增长或速度下降属于观察结果，需结合缓存、温度与日志分析原因。具体通过阈值按模型、硬件及业务需求配置。

## 4. 实现结构

```text
PC 浏览器
  └─ 控制服务（会话、任务、结果）
       ├─ 大模型适配器 ── Host 上的 rkllm3-server ── RK1828
       ├─ 压测执行器 ──── 同一个大模型适配器
       ├─ 设备采集器 ──── ADB / 可用的板端监控接口
       └─ 结果存储 ────── 配置、逐请求记录、遥测、报告
```

ADB 用于设备发现、环境检查、日志读取和必要的端口转发。大模型调用方式以实际 SDK 为准：

1. 若板端已有流式 HTTP 服务，优先直接接入其真实接口。
2. 若接口兼容 OpenAI Chat Completions，使用对应协议适配器；不能仅凭接口名称假设完整兼容。
3. 若仅有 SDK 或命令行示例，先完成最小板端包装服务，明确模型加载、会话隔离、流式输出和取消行为。

控制服务与压测器优先使用 Python，网页先参考 SDK 自带的 Flask 示例。第一版先完成可独立运行的命令行压测，再接入网页；UI 与 CLI 复用同一套执行和统计逻辑。具体依赖版本在初始化时确定。

建议目录（尚未创建）：

```text
backend/          控制接口、推理适配器、设备采集
benchmark/        测试执行、指标统计、报告生成
frontend/         概览、交互演示、压测、结果页面
cases/            演示提示词、压测输入、基本输出检查
configs/          设备、模型、负载配置样例
scripts/          环境检查与启动脚本
tests/            协议解析、指标统计、任务生命周期测试
results/          每轮测试的记录与报告
```

每轮生成唯一 run_id，保存模型/SDK/硬件信息、代码版本、测试集版本、完整配置、逐请求时间和 token 统计、错误信息及遥测。API 凭据不得写入结果文件；真实业务文本的输出留存应可配置。

## 5. 分阶段实施与验收

### 阶段一：设备与单模型基线

- 通过 ADB 或 SSH 连接 Host，使用 `rknn-smi` 识别加速器并采集硬件配置。
- 确认 SDK、模型文件、量化方式、上下文上限、启动命令和推理接口。
- 跑通一条真实问答，确认执行后端并保留日志。
- 完成 CLI 基线压测和逐请求结果落盘。

验收：能够重复执行同一配置，输出真实结果；缺失指标明确标注，失败可定位。

### 阶段二：现场演示 MVP

- 完成设备概览和带性能信息的流式聊天。
- 接入预置演示场景和基本输出检查，实时展示响应指标。
- 提供单请求、输入长度、并发三类短压测及结果导出。

验收：从检查设备到查看压测报告形成完整闭环；界面能够处理断连、超时和流中断，保留已产生的结果。

### 阶段三：边界与稳定性

- 扩展负载矩阵、长稳测试和资源时间序列。
- 增加配置对比，产出推荐运行区间与已知限制。
- 验证请求失败、客户端断开和服务恢复后的持续可用性。
- 输出长稳报告，记录失败时刻、资源变化、性能下降和恢复过程。

验收：报告说明可用配置、性能下降条件及失败边界；结论有实测记录支撑。具体性能达标线应在业务需求和首轮基线明确后制定。
